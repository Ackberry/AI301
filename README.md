## Understanding the Issue

### Problem Description
KHI (Kubernetes History Inspector) currently has two modes: server mode (browser) and job mode (headless). Within job mode, there is no way to add a local file via CLI. The upload - then - verify currently exists in browser mode only. To solve this, this adds an enhancement where the CLI can pick up a local file via filepath directly, provided khi is in job mode. 

### Expected Behavior

The user (in job mode) should be able to provide a local file directly via CLI (filepath), and have KHI read and verify it in place — no upload needed.

### Current Behavior

The user can only upload and verify a file via browser mode. 

### Affected Components

The backend is mainly involved: adjusting the backend components to safely accept a filepath in job mode, then verify the file with the existing verifier — reusing the upload token/provider machinery to represent the local file. The frontend isn't really involved, since the CLI example is generated by the backend and just rendered as-is by the frontend, so it updates automatically.

- **Approach decisions:** 
The core call was to reuse the existing upload abstractions instead of building a parallel path — represent the local file as a token + provider (the same ones uploads use) so the existing verifier and every downstream consumer stay unchanged. A few specifics fell out of that:

Read the file in place rather than copying it into the store — audit logs can be multiple GB, so copying would double disk/IO for nothing.
Pass the path inside --job-inspection-values keyed by field ID (consistent with text inputs), and emit a placeholder path in the generated command since the browser can't produce a real one.
Gate local-path handling to job mode explicitly, so server mode never touches local paths.
Decisions made or confirmed with the maintainer. These were the calls that touched shared design or safety, so I surfaced them rather than deciding unilaterally:

Dispatch providers by token GetType() — I proposed it, the maintainer confirmed it matched his intent.
Allow / in the local-file token — the upload check blocks slashes to stop path traversal from untrusted web clients, but in job mode the path comes from the trusted operator's own CLI, so it's safe; the maintainer agreed with that reasoning.
A concurrency fix the maintainer caught — a concurrent-map read on the verifier — resolved by reading it under its lock before the goroutine. We also flagged the new GetFileFieldIDs accessor since it opened up a type that was intentionally kept closed.

## Pull Request

**PR Link:** [https://github.com/GoogleCloudPlatform/khi/pull/829](https://github.com/GoogleCloudPlatform/khi/pull/829)

**PR Description:** Adds support for file-input inspection types (like OSS Kubernetes audit logs) in Job mode.

Before this change, the Job-mode command generated in the New Inspection dialog couldn't represent local file inputs, so file-based inspections couldn't be reproduced headlessly. This PR makes the generated command include a placeholder path for file fields, and makes the Job-mode runner load a local file from that path.

The main pieces:

GenerateJobModeCommand now emits a placeholder path in --job-inspection-values for each file field, and a new FormFieldSetMetadata.GetFileFieldIDs() lets it find which fields are files.
A new LocalFileUploadToken and InPlaceUploadFileStoreProvider read the file at its given path in place.
UploadFileStore now picks a provider based on the token's GetType(), so local-file tokens read through the in-place provider while the existing browser-upload flow is unchanged. The store is now set up in both server and job mode.
FileFormTask loads a local path from the request values when running in Job mode, and otherwise falls back to the existing upload flow.
Testing: added unit tests for the in-place provider read, the command generation with a file field, and the local-file load-and-verify path. The full suite passes with go test ./... -args -skip-cloud-logging=true, and I verified end to end by running an OSS file-input inspection in Job mode against a local JSONL file and confirming it produced a .khi output.

Frontend work is not done in this PR. The command preview already renders the placeholder correctly since the component just displays whatever the backend generates, so no frontend change is needed for correctness. An optional hint telling users to replace the placeholder path could be a follow-up.
